# Задание 1

Преимущества:
1. Активный Master и пассивный Slave
Быстрое аварийное переключение: при падении основного узла резервный сервер уже содержит копию данных и готов мгновенно взять нагрузку на себя.
Отсутствие задержек репликации для клиентов: так как чтение и запись идут в одну точку мастера, пользователи никогда не увидят устаревшие данные из-за асинхронности.
Безопасное обслуживание: резервное копирование, регламентные работы и обновление версий СУБД можно проводить на пассивном сервере без нагрузки на активный мастер.
2. Master и несколько Slave-серверов
Масштабирование чтения: добавление новых реплик позволяет пропорционально наращивать пропускную способность кластера для SELECT-запросов.
Разгрузка Master-сервера: ресурсы основного узла освобождаются от тяжёлых выборок и целиком выделяются под критичные транзакции записи.
Изоляция нагрузок: отдельные Slave-узлы можно закрепить за разными задачами — один под пользовательский трафик, второй под тяжёлую аналитику, третий под бэкапы.
Высокая доступность пула чтения: при сбое одного из Slave-серверов балансировщик просто перенаправляет запросы на оставшиеся живые реплики.  

# Задание 2

1. Разграничение данных
  Вертикальный шардинг: разделение сущностей по изолированным базам:
    База Users DB (users) — изолированный сервис под частые обновления и рост пользовательской базы.
    База Catalog DB (books, stores) — витрина и точки продаж, данные статичны и подвержены высокой нагрузке на чтение.
  Горизонтальный шардинг:
    Таблицы books и stores не шардируются.
   Таблица users шардируется по ключу user_id через хэширование: четные ID направляются в Шард 1, нечетные — в Шард 2.
2. Режимы работы серверов
    Sharding Proxy / API Gateway: маршрутизирует запросы каталога в Catalog DB, а транзакции пользователей распределяет между шардами по вычисленному хэшу.
    Мастера шардов пользователей: работают в режиме запись и чтение, обрабатывая запись и чтение для своего сегмента.
    Слейвы шардов пользователей: работают в режиме read_only = 1, выступая резервом на случай аварии и узлом для бэкапов.
    Мастер каталога: работает в режиме Read/Write, принимая редкие административные правки.
    Реплики каталога: работают в режиме read_only = 1, забирая на себя весь поисковый SELECT-трафик клиентов.
